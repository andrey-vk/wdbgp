`wdbgp` скачивает категоризированные IPv4/IPv6 CIDR-фиды, формирует каталог
сервисов и анонсирует выбранные пользователями префиксы их роутерам через BGP.

Это один статически собранный Go-бинарник с Vue 3 SPA админ-интерфейсом на
PrimeVue v4 + Tailwind CSS, HTTP API сервером, SQLite-хранилищем и собственным
BGP-спикером. Админка включает страницы Dashboard, Users, Modes, Feeds, Adapters,
Settings и Debug. Пользовательская страница позволяет выбирать категории сервисов
с веб-аутентификацией. Маршруты анонсируются каждому пиру напрямую из таблицы
маршрутов в памяти.

## Режимы каталогов

Встроены режимы `OpenCCK` с широким покрытием сервисов на базе ASN и общей
инфраструктуры и `IPRanges` с диапазонами провайдеров, платформ, CDN, сетей и
privacy-сервисов из
[antonme/ipranges](https://github.com/antonme/ipranges).

Администратор может включать и выключать режимы и назначать каждому фиду режим.
У пользователя есть один активный режим и независимый сохранённый выбор
категорий и сервисов для каждого режима. В BGP попадают только маршруты
активного режима. Существующие базы автоматически переносятся в `OpenCCK` без
изменения текущего выбора.

По умолчанию пользователь не может менять режим, пока администратор явно не
разрешит это. Отключённые режимы сохраняют загруженные данные и выборы, но не
создают маршруты. Диагностика CIDR работает для одного выбранного режима и
показывает только пользователей, у которых этот режим активен.

Встроенный адаптер IPRanges загружает merged IPv4/IPv6-списки upstream и
раскладывает их по отдельным сервисам каталога. Upstream объединяет публичные
данные провайдеров, диапазоны по ASN и адреса, полученные через DNS, поэтому
охват списков различается по сервисам. Изначально режим отключён: перед
настройкой пользователей его нужно включить и синхронизировать фиды.

Режим `sing-box SRS` обеспечивает поддержку бинарного формата rule-set sing-box
(файлы `.srs`). Эти файлы содержат IP CIDR-диапазоны, скомпилированные из geoip
или пользовательских источников. В дистрибутив входит встроенный адаптер,
который скачивает и распаковывает SRS-файлы, извлекая все CIDR. Для примера
добавлен выключенный по умолчанию фид для geoip России (`geoip-ru.srs`).

## Сетевая модель

Контейнер является самостоятельным BGP speaker со своим `veth`-адресом и не
изменяет RouterOS через API.

- Пользовательские CIDR определяют пользователя веб-интерфейса. Побеждает самая
  специфичная подходящая сеть.
- IP BGP peer и ASN определяют роутер, которому экспортируются маршруты.
- Next hop должен быть достижим с клиентского роутера по нужному VPN-маршруту.

Не публикуйте HTTP и TCP/179 в недоверенные сети.

## Веб-аутентификация

Режим веб-аутентификации пользователя управляет доступом к странице выбора:

- **network** — определение по IP, совпадающему с CIDR пользователя
- **login** — вход по логину/паролю
- **both** — совпадение IP И учётные данные
- **any** — совпадение IP ИЛИ учётные данные (любой из способов)

Учётные данные (логин + bcrypt-хеш пароля) управляются через админку для каждого
пользователя. Страница `/login` обслуживает аутентификацию по учётным данным.
`WDBGP_DEFAULT_WEB_AUTH` задаёт режим по умолчанию для новых пользователей
(по умолчанию: `network`).

## Фиды

При первом старте добавляются основные и beta-фиды OpenCCK для IPv4 и IPv6.
Первое обновление начинается сразу после запуска, последующие выполняются через
`WDBGP_SYNC_INTERVAL` секунд. При ошибке старый успешно загруженный снимок фида
сохраняется.

См. [Адаптеры фидов](docs/adapters.ru.md) — документация по API адаптеров,
встроенным адаптерам и формату фидов.

Поддерживаются также один entry-объект и массив entry-объектов. Префиксы
нормализуются и дедуплицируются. Выбор категории автоматически включает новые
сервисы, которые позже появятся в ней.

Фиды можно добавлять, редактировать, включать, выключать и удалять через
админку. Выключение сохраняет последний загруженный снимок и пользовательский
выбор в базе, но исключает сервисы и префиксы фида из каталога и BGP-анонсов.
После включения снимок снова используется до следующей синхронизации. Изменение
URL очищает старый снимок, а удаление полностью удаляет фид.

В админке также доступна диагностика CIDR. Для IP-адреса или подсети она
показывает полное и частичное покрытие сервисами, их совокупное покрытие и
покрытие выбранными категориями и сервисами каждого включённого пользователя
до и после применения его эффективных фильтров маршрутов.

## Фильтрация маршрутов

Администратор задаёт глобальные списки allow и deny. Пустой allow разрешает все
выбранные из фидов префиксы, а deny вычитается из результата. Вычитание точное:
если запретить `1.1.1.1/32` внутри выбранного `1.0.0.0/8`, сеть `/8` будет
раздроблена на CIDR, которые больше не покрывают `1.1.1.1`.

Каждый пользователь может наследовать глобальные списки, дополнять их
пользовательскими списками или использовать полный пользовательский override. В
режиме дополнения allow и deny объединяются с глобальными списками перед
фильтрацией. Администратор отдельно разрешает пользователю редактировать режим
и списки через пользовательский интерфейс. Default routes из фидов всегда
отбрасываются, а расширение ограничено для защиты от случайного взрыва
количества префиксов.

Миграция фильтров маршрутов инициализирует глобальный deny распространёнными
private, loopback, link-local, documentation, benchmark, multicast и reserved-сетями.

## Настройки

Все настройки приложения хранятся в базе данных и редактируются на странице
`/admin/settings`. Переменные окружения всегда переопределяют сохранённые значения —
настройки из ENV затемнены и показывают подсказку. Настройки не из ENV применяются
сразу где возможно; BGP и сетевые требуют перезапуска.

Глобальные списки фильтрации маршрутов также находятся на этой странице.

## MD5-аутентификация динамических пиров

Динамические пиры (`peer_ip` = `0.0.0.0`/`::`) обычно определяются только по
ASN — ядерному `TCP_MD5SIG` нужен конкретный адрес, заданный заранее,
которого у wildcard-пира нет. `WDBGP_DYNAMIC_PEER_MD5_MATCH` (по умолчанию
`false`) закрывает этот пробел: NFQUEUE-обработчик проверяет перебором
настоящую TCP MD5 (RFC 2385) подпись входящих SYN-пакетов против паролей
настроенных динамических пиров, аутентифицируя их криптографически, а не
только по ASN. Требует `CAP_NET_ADMIN` и ядро Linux с поддержкой
`nfnetlink_queue`; бинарник `nft`/`iptables` нигде не нужен — правило
перенаправления устанавливается автоматически, полностью через netlink.

См. [MD5-аутентификация динамических BGP-пиров](docs/dynamic-peer-md5.ru.md) —
требования, примеры systemd/Docker для запуска вне контейнера RouterOS, и
диагностика.

## Запуск

```sh
docker run --rm \
  -p 8080:8080 \
  -p 179:179 \
  -v wdbgp-data:/data \
  -e WDBGP_ADMIN_PASSWORD=change-me \
  -e WDBGP_SESSION_SECRET=a-long-random-secret \
  -e WDBGP_LOCAL_ASN=64512 \
  -e WDBGP_ROUTER_ID=172.31.255.2 \
  -e WDBGP_BGP_LOCAL_ADDRESS=172.31.255.2 \
  -e WDBGP_BGP_LOCAL_ADDRESS_V6=fd00:31:255::2 \
  wh1ted/wdbgp:alpha
```

Откройте `/admin`, добавьте пользователей и настройте выбор сервисов. Страница
`/` определяет пользователя по исходному IP. Если приложение находится за
доверенным reverse proxy, включите `WDBGP_TRUST_PROXY_HEADERS=true`.

Веб-интерфейс доступен на русском и английском языках. Язык выбирается по
`Accept-Language` браузера, а явный выбор `EN`/`RU` сохраняется в cookie.
Fallback-язык задаётся через `WDBGP_DEFAULT_LANGUAGE` и по умолчанию равен `en`.

Cookie админки по умолчанию используют `WDBGP_ADMIN_COOKIE_SECURE=auto`. Если
web-интерфейс админки доступен без HTTPS, обязательно установите
`WDBGP_ADMIN_COOKIE_SECURE=false`; иначе браузер может не сохранить session
cookie и после правильного пароля снова перекинет на страницу входа. Принудите
`true` только когда админка всегда открывается через HTTPS.

### Резервное копирование и автовосстановление базы данных

Перед выполнением ожидающих миграций схемы сервер создаёт копию текущей базы
в `WDBGP_BACKUP_DIR`. Из копии исключаются кешированные данные фидов
(`catalog_entries`), которые можно восстановить синхронизацией. Отключить
можно через `WDBGP_BACKUP_ENABLED=false`.

Если база была создана более новой версией ПО, при запуске включается
**degraded mode**: веб-интерфейс показывает страницу с ошибкой версии (RU/EN),
BGP и синхронизация не запускаются.

При `WDBGP_AUTO_RESTORE_ENABLED=true` сервер ищет в `WDBGP_BACKUP_DIR` бэкап,
соответствующий текущей версии, и восстанавливает его. Несовместимая база
сохраняется с суффиксом `.incompatible-v<N>.sqlite3`. Если подходящий бэкап
не найден — degraded mode с описанием ошибки.

Эндпоинт `/status` возвращает операционные данные в JSON. Доступ требует
либо IP клиента из `WDBGP_STATUS_ALLOWED` (CIDR через запятую), либо
заголовок `Authorization: Bearer <WDBGP_STATUS_TOKEN>`. Если ни то, ни другое не задано — 403.

### BGP Communities

Каждой категории и сервису назначается BGP Large Community (`ASN:0:Number`).
Значения сообществ генерируются автоматически по читаемой человеком схеме (группы: 10000, 20000, 30000…;
сервисы: группа+1, группа+2…) и могут редактироваться администратором на странице `/admin/communities`.
Эти сообщества добавляются к каждому анонсируемому BGP-префиксу, позволяя настраивать
маршрутизацию по категориям и сервисам на стороне роутера.

Номера сообществ назначаются **отдельно для каждого режима каталога**: одна и та же
категория может иметь разные номера в разных режимах, поэтому перевод пользователя в
другой режим меняет смысл всех правил на его роутере, сопоставляющих communities.

Страница выбора для конечного пользователя тоже показывает номер community рядом с
каждой категорией и сервисом — так пользователю, настраивающему фильтрацию на своём
роутере, не нужно спрашивать номера у администратора.

#### Экспорт communities

`GET /api/communities` отдаёт полную карту communities в JSON — для генерации политик
на нижестоящих роутерах вместо копирования номеров руками. Авторизация такая же, как у
`/status`: IP клиента из `WDBGP_STATUS_ALLOWED` либо заголовок
`Authorization: Bearer <WDBGP_STATUS_TOKEN>`. Админская сессия тоже принимается, чтобы
страница Communities могла отдать тот же документ файлом.

Все режимы находятся в одном документе, потому что плоская карта «community → имя» не
способна выразить пер-режимную нумерацию. Каждая категория и сервис несут свой номер,
готовую форму для провода (`<asn>:0:<номер>`) и текущие счётчики префиксов IPv4/IPv6 —
резко упавший счётчик категории служит ранним признаком поломки фида.

Синхронизация фида публикует каталог и генерирует для него communities двумя отдельными
транзакциями; экспорт читает каталог, назначения и счётчики префиксов как единый
согласованный снимок — генерируя недостающие назначения внутри той же транзакции —
а не отдаёт сервис без назначения. Этот снимок охватывает все режимы в документе, а не
каждый режим по отдельности: фид, общий для нескольких режимов, публикует обновление
сразу для всех них, поэтому чтение режимов по отдельности могло бы показать обновление
применённым к одному режиму, но ещё не к другому. ASN и настроенный ASN, используемые
для рендеринга каждой строки `large_community` и поля `asn_configured`, читаются уже
после того как вся эта работа с базой завершена, а не до неё — и оба перепроверяются
ещё раз сразу после рендеринга, повторяя его, если изменилось хоть одно из значений
(обычное сохранение настройки меняет настроенный ASN вообще без перезапуска BGP), —
так изменение, завершившееся пока экспорт ещё собирал данные (или даже во время самого
рендеринга), никогда не оставит ответ, описывающий значения, уже переставшие
соответствовать реальности. Если за весь бюджет попыток хотя бы одно из значений так и
не устоялось, эндпоинт отвечает `503 Service Unavailable` вместо того чтобы отдать
документ, уже заведомо устаревший, — стоит повторить запрос, когда настройка или
перезапуск устаканятся.

```console
$ curl -sH "Authorization: Bearer $WDBGP_STATUS_TOKEN" http://wdbgp:8080/api/communities
{
  "schema_version": 1,
  "generated_at": "2026-09-30T18:33:53Z",
  "asn": 64512,
  "bgp_running": true,
  "modes": [
    {
      "mode_id": 1,
      "mode_name": "OpenCCK",
      "enabled": true,
      "categories": [
        {
          "name": "adobe",
          "community": 10000,
          "large_community": "64512:0:10000",
          "prefix_count_v4": 352,
          "prefix_count_v6": 33,
          "services": [
            { "name": "adobe.com", "community": 10001, "large_community": "64512:0:10001",
              "prefix_count_v4": 143, "prefix_count_v6": 13 }
          ]
        }
      ]
    }
  ]
}
```

`asn` — это значение, которое работающий спикер реально проставляет в маршруты: снимок,
взятый при его старте, а не живая настройка `WDBGP_LOCAL_ASN`. Если настройку изменили
без перезапуска BGP, новое значение отдаётся отдельным полем `asn_configured` — так
сгенерированная политика всегда соответствует тому, что на проводе. Когда спикер не
запущен, `bgp_running` равно `false`, а в `asn` отдаётся значение из настроек.

Этот документ отражает желаемое состояние базы данных. Доставка на BGP-пиры асинхронна
и происходит по best-effort (изменение community, сброс или синхронизация фида сначала
коммитятся, а reconcile происходит уже после), и у этого эндпоинта нет способа привязать
конкретное экспортируемое значение к подтверждению, что оно реально дошло до пиров —
точная привязка потребовала бы ревизии, протянутой через все пути записи, способные
повлиять на анонсируемые маршруты, а это больше, чем пытается сделать этот эндпоинт.
`/api/admin/bgp/status` и статус по каждому пиру на странице Users — это уже существующий
способ проверить здоровье самой BGP-сессии.

Для опроса в ответе есть `ETag`, покрывающий содержимое документа, но не `generated_at`,
поэтому неизменившаяся карта отвечает `304 Not Modified`. Это слабый валидатор (`W/"…"`),
а не сильный — два ответа с одинаковым ETag семантически эквивалентны, но не побайтово
идентичны (`generated_at` отличается), именно для этого и существует слабое сравнение.
`If-None-Match` сопоставляется по RFC 7232 §2.3: слабым сравнением (игнорируя префикс
`W/` с любой стороны), по каждому валидатору в списке через запятую, а `*` подходит
всегда — а не только единственной точной строке, которую отдаёт сам этот эндпоинт:

```console
$ curl -sD- -o/dev/null -H "Authorization: Bearer $TOKEN" \
    -H 'If-None-Match: W/"b178345bbd…"' http://wdbgp:8080/api/communities
HTTP/1.1 304 Not Modified
```

`schema_version` меняется только при несовместимом изменении структуры документа.

#### Перенумерация

«Сгенерировать отсутствующие» только заполняет пропуски — существующие назначения
никогда не сдвигаются, поэтому запускать её после появления новых сервисов безопасно.
«Сброс к значениям по умолчанию» работает иначе: он отбрасывает все назначения и
нумерует заново, что молча обесценивает любую политику на стороне роутера,
сопоставляющую прежние значения, — и отказ выглядит как сетевая авария, а не как
изменение конфигурации. Поэтому сброс сначала спрашивает и показывает, какие именно
значения изменятся; на инстансе, где communities нарастали за несколько синхронизаций
фидов, это обычно *большая часть* из них.

В ответе предпросмотра рядом со списком изменений приходит `digest` — отпечаток того
состояния, из которого предпросмотр был построен, включая ID самого режима: два режима
с одинаковыми назначениями communities (обычное дело, если они используют общие фиды)
никогда не получат одинаковый digest — предпросмотр одного не может авторизовать сброс
другого. Применение (`{"confirm": true, "digest": "..."}`) должно вернуть этот же digest
обратно; если режим за это время изменился — синхронизация фида перегенерировала
communities, или другой админ отредактировал значение — digest больше не совпадает, и
сброс отклоняется (`409`) со свежим предпросмотром, вместо того чтобы молча
перенумеровать то, что никто на самом деле не проверял.

### Проверка адреса

На странице выбора конечного пользователя есть инструмент проверки адреса, отвечающий
на вопрос «почему этот IP в моём туннеле / не в нём»: вводится CIDR-префикс или адрес,
и в ответ приходит каждая категория/сервис каталога, покрывающая его (независимо от
того, выбрана ли она пользователем), выбрана ли она пользователем, и уберёт ли её
фильтр маршрутов до того, как она попадёт в провод. CIDR-блок, доставленный лишь
частично (например, /24 с одной выбранной /25 внутри), показывается как частичное
покрытие, а не схлопывается до того же вердикта, что и полностью доставленный запрос.
Это однопользовательское, read-only представление той же логики покрытия, что стоит
за админским инструментом
CIDR debug (`/admin/debug`), но ограниченное так, что вызывающий может увидеть только
свои собственные выборы и фильтры — параметров режима или пользователя, позволяющих
запросить чужие данные, здесь нет.

За этим стоит `GET /api/user/debug?cidr=`; режим и личность всегда берутся из
аутентифицированной сессии.

### Действующие фильтры

Глобальные и персональные фильтры маршрутов могут незаметно убирать префиксы, которые
пользователь иначе ожидал бы увидеть анонсированными. На странице выбора конечного
пользователя есть read-only раздел «действующие фильтры», видимый всем пользователям
независимо от того, разрешено ли им редактировать свои фильтры: он показывает их
`filter_mode` (`global`, `extend` или `override`) простым языком и итоговые
(эффективные) списки allow/deny. В режиме `extend` итоговые списки также разбиваются
по происхождению — глобальные и персональные, поскольку один объединённый список не
может показать, какая сторона внесла какую запись.

За этим стоит `GET /api/user/route-filters`, всё выводится из аутентифицированной
сессии — параметра, позволяющего запросить чужие фильтры, здесь нет.

### Журнал аудита

Append-only журнал того, кто что изменил, ограниченный действиями, которые чаще всего
порождают вопрос «что изменилось за последние сутки»: назначения communities (ручные
правки, reset, generate), фильтры маршрутов (глобальные настройки и персональные
переопределения), включение/выключение фида, перемещение пользователя между режимами
каталога и изменения выбора (как самостоятельные, так и сделанные админом напрямую).
Каждая запись содержит актора, действие, тип и ID объекта, время и снимок «до/после»
только изменившихся полей — запись не создаётся, если запрос фактически ничего не
изменил (например, повторная отправка того же значения фильтра, или обновление фида,
не трогающее `enabled`).

В этом коде пока нет множественной идентификации администраторов — админ-сессия это
единый общий пароль/токен, — поэтому актор для админского действия — `admin:<ip>`;
самостоятельное действие пользователя — `user:<id>`.

`GET /api/admin/audit-log` отдаёт записи с фильтрами `actor`/`action`/`object_type`/
`object_id`/`since`/`until` и пагинацией `limit`/`offset` (отображается на странице
админки «Журнал аудита»). Записи хранятся `audit_log_retention_days` дней (по умолчанию
30) и удаляются ежечасно вместе с очисткой снимков метрик.

### Изменения при синхронизации фидов

Каждая синхронизация, которая меняет записи фида, сохраняет, что она добавила и удалила:
сервисы и префиксы, добавленные сервисы разбиты по категориям. На странице фидов видны
последние 20 таких синхронизаций (`GET /api/admin/feeds/{id}/sync-changes`). Первый импорт
не записывается, так как сравнивать не с чем, а на фид хранятся не более 50 последних
синхронизаций с изменениями.

Выбор категории включает все её сервисы, поэтому синхронизация может добавить сервисы в выбранные пользователем категории без его действий. На странице пользователя появляется скрываемая заметка с сервисами, которые добавила синхронизация, по категориям — для выбранных им категорий в режиме, куда входит фид. Заметка сообщает о сервисах, а не о маршрутах: сервис может уже покрываться другим фидом и не добавить маршрута. Заметка охватывает последние 14 дней или период с момента последнего скрытия, что позже. `GET /api/user/feed-changes` отдаёт её, а `POST /api/user/feed-changes/ack` подтверждает просмотр до самой новой показанной записи, отдельно для режима.

### Журнал изменений пользователя

Страница пользователя показывает историю изменений за последние 30 дней, либо за срок хранения аудита, если он короче. В ней есть каждое изменение собственного выбора, фильтров маршрутов и режима пользователя, а также каждая синхронизация фида, которая добавила или удалила выбранный пользователем сервис. У каждой записи указано, кто её сделал: сам пользователь (`self`), администратор (`admin`, без адреса) или синхронизация фида с его названием. Изменения пользователя и администратора берутся из журнала аудита и хранятся `audit_log_retention_days` дней. Записи о синхронизациях берутся из `feed_sync_change_services`, которая очищается вместе с историей из 50 синхронизаций фида. `GET /api/user/change-log` отдаёт записи, сначала новые, не больше 200 на пользователя. Каждый список (категории, сервисы, маршруты) ограничен 100 элементами, остальное считается в `omitted`.

Синхронизация фида привязывается к истории пользователя, а не к его текущему выбору. Она попадает в лог, если в тот момент пользователь был в режиме фида и выбрал категорию сервиса или сам сервис. Выбор и режим на момент синхронизации берутся из журнала аудита. Каждое записанное изменение хранит состояние до себя, поэтому состояние на момент синхронизации — это состояние до первого изменения после неё, либо текущее состояние, если после неё изменений не было. Более поздняя смена выбора не переписывает то, что синхронизация значила для пользователя. Режимы, которые синхронизация достигла, фиксируются в момент её выполнения, поэтому поздние правки назначений фида режимам их тоже не переписывают. Синхронизация запоминает строку аудита, после которой была записана, поэтому изменение в ту же секунду упорядочивается по порядку записи, а не по времени.

Удаление фида сохраняет его прежние синхронизации в логе и записывает уход сервисов как удаление. Выборы, которые потеряли последний сервис, аудируются как изменения администратора. Эти записи удаляются, когда становятся старше срока хранения аудита.

История аккаунта начинается с его создания, а для аккаунтов, существовавших на момент обновления, — с обновления. Поэтому ID, который когда-то принадлежал удалённому аккаунту, никогда не показывает его историю.

Восстановление читает 2000 самых новых строк аудита аккаунта и 1000 самых новых синхронизаций, затрагивающих его категории. Синхронизация старше самой старой из них не привязывается, а не угадывается.

Отсюда два ограничения. Изменения выбора, записанные до появления payload с именами, хранят только количества, поэтому синхронизация, пришедшая до такого изменения, не может быть привязана и в лог не попадает. Кроме того, история доходит только до границы окна аудита.

### Матрица сообществ

Административная страница «Матрица сообществ» показывает в виде сетки номер группового сообщества каждой категории во всех режимах. Категория, у которой номер различается между режимами, или отсутствует в одном из них, помечается, и список можно сузить до помеченных категорий. Матрица также сравнивает номера на уровне отдельных сервисов: категория, у которой совпадает только групповой номер, но различается номер одного из сервисов (или он есть не во всех режимах), тоже помечается — вместе с числом таких сервисов. `GET /api/admin/communities/matrix` отдаёт ту же сетку в JSON.

Открытие матрицы читает только уже сохранённые номера сообществ — она никогда не генерирует недостающие сама, поэтому остаётся дешёвой даже на большом каталоге. Это значит, что режим, который давно не открывали и не регенерировали, может показывать категории как отсутствующие, даже если на самом деле всё в порядке. Перед тем как полагаться на сетку при переносе пользователя между режимами, нажмите кнопку «Сгенерировать недостающие» на странице (`POST /api/admin/communities/matrix/generate`) — она заполнит недостающие номера сразу во всех режимах.

### Оповещения об отключениях и история префиксов

Реальное число анонсируемых префиксов каждого включённого пользователя — после
выбора и фильтров маршрутов, то же число, что использует предпросмотр влияния
изменений — измеряется каждые 5 минут и отображается графиком на собственной
странице этого пользователя в админке. Когда измерение падает на
`alert_prefix_drop_threshold_percent`% (по умолчанию 50) или больше по сравнению
с последним нормальным измерением, и это базовое значение было не меньше
`alert_prefix_baseline_minimum` (по умолчанию 10 — чтобы обычный шум маленькой
выборки, например 2 префикса стали 1, не считался «падением»), на
`alert_webhook_url` отправляется JSON-документ — по умолчанию пусто, то есть
оповещения выключены; история префиксов при этом всё равно ведётся. Второй
документ отправляется, когда пользователь восстанавливается. Оба порога не имеют
значения, пока не настроен URL вебхука.

```json
{"event": "prefix_drop", "user_id": 23, "user_name": "alice",
 "detected_at": "2026-10-08T03:14:00Z",
 "baseline_v4": 900, "baseline_v6": 100, "current_v4": 90, "current_v6": 10,
 "drop_percent": 90}
```

Падение никогда не сообщается повторно, пока пользователь остаётся «внизу» — это
конечный автомат состояний, а не порог, проверяемый заново на каждом тике — а
«восстановление» измеряется относительно того, что было нормой непосредственно
перед инцидентом, а не относительно текущего значения. Само состояние (и базовое
значение) отслеживается всегда, независимо от того, настроен ли вебхук вообще;
падение, которое не удалось доставить — оповещения были выключены, или запрос не
прошёл — остаётся помеченным как недоставленное и повторяется на каждой
следующей проверке, как только вебхук становится достижим, уже со свежим
значением с этой проверки. Если падение разрешилось раньше, чем о нём вообще
успели сообщить, «восстановление» по нему тоже не сообщается — говорить
оператору, что всё в порядке, про инцидент, о котором ему никогда не сообщали,
только сбивает с толку. Восстановление, о котором сообщили, но не удалось
доставить, повторяется точно так же, как и падение, а не отправляется один раз
и забывается — оно несёт собственные базовое значение и длительность инцидента,
зафиксированные в момент обнаружения, поскольку живое базовое значение в строке
пользователя сразу же переключается на новую норму и не годится для повторной
попытки позже; свежее падение, наступившее раньше доставки такого
восстановления, отменяет его целиком — по той же причине «сбивает с толку, а не
помогает». Доставка происходит только после того, как измерены и
записаны ВСЕ пользователи в рамках этой проверки, а не вперемешку с измерением —
поэтому один медленный или недоступный получатель не может задержать измерение
остальных; каждая попытка повторяет транзиентный сбой в течение нескольких
секунд, прежде чем сдаться. Сознательно НЕ завязана на существующую настройку
`metrics_enabled` — она управляет собственным фоновым сбором данных дашборда,
другой функциональностью без очевидной связи по названию, и администратор,
который задал `alert_webhook_url`, но отдельно не заметил и не включил эту
настройку, иначе вообще не получал бы оповещений, причём без малейшего
указания, почему. История всё равно хранится `metrics_history_days` — так же,
как уже работают история по фидам и агрегированная история пользователей на
дашборде — но очищается независимо от `metrics_enabled` по той же причине.

### Экспорт / импорт конфигурации

Административная страница «Экспорт / Импорт» экспортирует пользователей, глобальные
фильтры маршрутов, сообщества и режимы этого инстанса одним JSON-документом,
показывает предпросмотр того, что изменит загруженный документ, и применяет его.
Фиды не входят в область — членство режима в фиде записывается по имени фида, и
имя, которому целевой инстанс не может найти соответствие, просто сообщается и
пропускается, а не проваливает весь импорт целиком — так же как и шаблоны выбора,
которых пока не существует.

Импорт только дополняет: сущность (пользователь или режим), которая уже есть в этом
инстансе, но не упомянута в загруженном документе, остаётся без изменений и никогда
не удаляется. У сущности, которую документ упоминает, собственные поля — у
пользователя сети, фильтры маршрутов и выбор; у режима членство в фидах — заменяются
целиком, в точности как при ручном редактировании, за одним исключением: назначения
сообществ объединяются (upsert), а не заменяются, поскольку список сообществ в
частичном документе не претендует на то, чтобы быть единственным источником истины
для всей нумерации режима, и молчаливое стирание неупомянутой записи имело бы вполне
реальные последствия для BGP-сообществ. BGP-пароль никогда не экспортируется
(`has_bgp_password` сообщает только о том, установлен ли он) и импорт его никогда не
трогает — у вновь создаваемого пользователя пароля нет, администратор должен задать
его вручную; у уже существующего пользователя пароль остаётся точно таким же, как был.

Применение всегда сначала показывает предпросмотр — `POST /api/admin/config/import/preview`
ничего не пишет и возвращает как разницу с текущей конфигурацией этого инстанса, так
и дайджест, связывающий воедино загруженный документ и эту текущую конфигурацию.
`POST /api/admin/config/import` пересчитывает тот же дайджест изнутри той самой
транзакции, что применяет импорт, непосредственно перед любой записью, и отказывает
с `409`, если он не совпадает — либо изменился сам загруженный документ, либо уплыла
живая цель под ним (правка другого администратора, случившаяся вплоть до этого
момента) — так что после проверки не остаётся зазора, в который могла бы незаметно
попасть параллельная правка. Та же дисциплина «подтверждение по дайджесту», что уже
установлена для «Сброса к значениям по умолчанию» (выше), только связывающая не один
документ, а оба. `POST
/api/admin/config/diff` принимает два документа напрямую и возвращает их разницу,
ничего не читая из этого инстанса и не записывая в него — для сравнения двух
экспортов, в том числе с разных инстансов, без импорта ни одного из них.

Документ, чья `schema_version` не совпадает с версией этого инстанса, отклоняется
сразу и предпросмотром, и импортом, а не молча декодируется с отсутствующими полями
как нулевыми значениями — та же проверка действует на уровень глубже, для самого
`global_filters`: пустой `{}` там присутствует и не равен null, но всё равно
декодируется в пустые allow/deny и очистил бы оба списка, поэтому собственные ключи
`allow`/`deny` внутри него тоже обязательны. Сети импортируемого пользователя
проверяются на пересечение с сетями всех остальных активных пользователей — та же
проверка, что уже применяют обычные формы создания/редактирования пользователя.
Некорректный глобальный фильтр отклоняется до того, как закоммитится что-либо ещё из
документа, а не после. Обмен BGP-идентичностями пиров между двумя пользователями в
одном импорте сначала временно убирает каждую изменяемую идентичность в сторону — в
заглушку, зарезервированную с учётом того, что уже хранится у пользователей этого
инстанса, и с учётом каждой идентичности, которую этот же импорт вот-вот назначит
по-настоящему, а не просто считая её свободной; пользователь, чей режим каталога не
находит соответствия на этом инстансе, пропускается ещё до этого шага, а не после,
поэтому он никогда не остаётся навсегда с этой заглушкой вместо своей идентичности.

Глобальные фильтры маршрутов — единственная часть документа, которую импорт
применяет через слой настроек (`internal/settings`) в отдельной транзакции, а не тем
же прямым запросом к базе, которым применяется остальной документ — этот слой
хранит собственный кеш в памяти, который прямая запись оставила бы устаревшим до
следующего перезапуска. Применение также перезагружает каждого созданного или
изменённого пользователя в собственный список пиров работающего BGP-спикера —
одного `Reconcile` недостаточно, он сверяет маршруты только с уже известными ему
пирами, поэтому новому или вновь включённому пиру для реального старта сессии нужен
именно этот шаг.

### Предпросмотр влияния изменений

Четыре админских действия меняют набор префиксов, которые реально получает
пользователь: глобальные фильтры маршрутов, персональное переопределение фильтра у
пользователя, состав фидов режима и перенос пользователя в другой режим каталога.
Каждое из них теперь сначала показывает предпросмотр влияния — диалог со списком
затронутых пользователей (счётчики IPv4/IPv6 до и после), отметкой тех, кто потеряет
маршруты, и итоговым изменением — а сохранение происходит только после явного
подтверждения. Если ничьи счётчики на самом деле не изменятся, сохранение проходит
сразу — диалог прерывает процесс только когда там действительно есть что проверить.

Обобщает тот же приём, что уже используется для предпросмотра «Сбросить к значениям
по умолчанию» (выше): реально выполнить изменение внутри транзакции базы данных,
измерить результат по каждому затронутому пользователю, а затем всегда откатить —
поэтому предпросмотр не может разойтись с тем, что изменение сделает на самом деле,
ведь это оно и есть, просто отменённое после измерения. В отличие от предпросмотра
сброса, здесь нет контракта digest/устаревания — применение изменения после
предпросмотра это обычное сохранение (форма настроек, диалог редактирования
пользователя, редактор фидов режима), вызванное как обычно.

`POST /api/admin/settings/preview-filters` и `POST /api/admin/modes/{id}/feeds/preview`
отдают диалоги для глобальных фильтров и состава фидов режима, каждый принимает то же
тело запроса, что и соответствующий endpoint сохранения. Диалог редактирования
пользователя сохраняет filter_mode, filter_override, фильтры маршрутов и
catalog_mode_id одним PUT-запросом, поэтому и предпросмотр у них один —
`POST /api/admin/users/{id}/preview` симулирует итоговое состояние целиком в одной
пробной транзакции: симуляция каждого поля по отдельности относительно исходного
состояния могла бы пропустить (или ошибочно показать) влияние, которое на самом деле
даёт только их сочетание. Все три endpoint'а ничего не меняют — пробная транзакция
никогда не коммитится.

### Проверка и ограничения

Все значения проверяются при запуске с понятными сообщениями об ошибках. Если не указаны, применяются значения по умолчанию.

| Переменная | Ограничения |
| --- | --- |
| `WDBGP_PORT` / `WDBGP_BGP_PORT` | Целое число 1–65535 |
| `WDBGP_LOCAL_ASN` | Целое число 1–4294967295 |
| `WDBGP_SYNC_INTERVAL` | Целое число ≥1 (секунд) |
| `WDBGP_ROUTER_ID` | Корректный IPv4-адрес |
| `WDBGP_BGP_LOCAL_ADDRESS` | Корректный IPv4-адрес |
| `WDBGP_BGP_LOCAL_ADDRESS_V6` | Корректный IPv6-адрес (или пусто для отключения IPv6-анонсов) |
| `WDBGP_SECURITY_HEADERS` | Логическое; включает HTTP security headers (CSP, HSTS, X-Frame-Options и др.) |
| `WDBGP_RATE_LIMIT_LOGIN` | Целое число 1–1000; запросов входа в минуту (по умолчанию 5) |
| `WDBGP_RATE_LIMIT_ADMIN` | Целое число 1–1000; запросов admin API в минуту (по умолчанию 30) |
| `WDBGP_SESSION_MAX_AGE` | Целое число 60–31536000; срок действия session cookie в секундах (по умолчанию 28800 = 8 часов) |
| `WDBGP_LOG_LEVEL` | DEBUG, INFO, WARN, ERROR, FATAL, PANIC (по умолчанию INFO) |
| `WDBGP_LOG_FORMAT` | text или json (по умолчанию text) |
| `WDBGP_TRUST_PROXY_HEADERS` | Логическое; доверять заголовку X-Forwarded-Proto для определения безопасности cookie |
| `WDBGP_DEFAULT_WEB_AUTH` | network, login, both или any |
| `WDBGP_JS_TIMEOUT` | Целое число ≥1; таймаут выполнения адаптера в секундах (по умолчанию 120) |
| `WDBGP_JS_MAX_SOURCE` | Целое число ≥1; макс. размер исходного кода адаптера в байтах (по умолчанию 1 МиБ) |
| `WDBGP_JS_MAX_RESPONSE` | Целое число ≥1; макс. байт HTTP-ответа на запрос (по умолчанию 16 МиБ) |
| `WDBGP_JS_MAX_TOTAL` | Целое число ≥1; макс. суммарных байт HTTP-ответов за запуск адаптера (по умолчанию 64 МиБ) |
| `WDBGP_JS_MAX_ENTRIES` | Целое число ≥1; макс. CIDR-записей на выходе адаптера (по умолчанию 1 000 000) |
| `WDBGP_JS_MAX_REQUESTS` | Целое число ≥1; макс. HTTP-запросов за запуск адаптера (по умолчанию 200) |
| `WDBGP_JS_MAX_CALL_STACK` | Целое число ≥1; макс. глубина call stack JavaScript (по умолчанию 1000) |
| `WDBGP_DYNAMIC_PEER_MD5_MATCH` | Логическое; включает MD5-проверку подписи динамических пиров через NFQUEUE (по умолчанию false, см. [docs/dynamic-peer-md5.ru.md](docs/dynamic-peer-md5.ru.md)) |
| `WDBGP_DYNAMIC_PEER_MD5_QUEUE_NUM` | Целое число 0–65535; номер NFQUEUE (по умолчанию 0) |

Приложение предоставляет эндпоинт `/status` для мониторинга состояния, возвращающий базовую информацию о работоспособности и версии в формате JSON.

## Миграции

Миграции SQLite выполняются автоматически и транзакционно при каждом запуске
любой команды. Существующая база Python-версии обновляется на месте без смены
формата данных. Применённые версии записываются в `schema_migrations`.

Приложение не запускается с неизвестной более новой версией схемы. Перед
крупным обновлением всё равно рекомендуется остановить контейнер и скопировать
постоянный том `/data`.

```sh
docker run --rm -v wdbgp-data:/data wh1ted/wdbgp:latest migrate
docker run --rm -v wdbgp-data:/data wh1ted/wdbgp:latest stats
docker run --rm -v wdbgp-data:/data wh1ted/wdbgp:latest sync
```

## Разработка

Go-сборка встраивает собранный фронтенд (`webgui/dist`) через `go:embed`,
поэтому сначала нужно собрать фронтенд — иначе `go build`/`go vet`/
`go test ./...` не пройдут на свежем чекауте, так как `webgui/dist` появится
только после сборки.

```sh
cd webgui && npm install && npm run build && cd ..
go test ./...
go vet ./...
go build ./cmd/wdbgp
docker build -t wdbgp:latest .
```

## Контейнер на MikroTik

Пример использует `172.31.255.2` для контейнера и `172.31.255.1` для RouterOS:

```routeros
/interface/veth/add name=veth-wdbgp address=172.31.255.2/30 gateway=172.31.255.1
/interface/bridge/add name=br-containers
/interface/bridge/port/add bridge=br-containers interface=veth-wdbgp
/ip/address/add address=172.31.255.1/30 interface=br-containers

/container/envs/add list=wdbgp key=WDBGP_ADMIN_PASSWORD value="change-me"
/container/envs/add list=wdbgp key=WDBGP_SESSION_SECRET value="replace-with-a-long-random-secret"
/container/envs/add list=wdbgp key=WDBGP_LOCAL_ASN value="64512"
/container/envs/add list=wdbgp key=WDBGP_ROUTER_ID value="172.31.255.2"
/container/envs/add list=wdbgp key=WDBGP_BGP_LOCAL_ADDRESS value="172.31.255.2"

/container/mounts/add name=wdbgp-data src=disk1/wdbgp-data dst=/data
/container/add remote-image=wh1ted/wdbgp:latest interface=veth-wdbgp \
  root-dir=disk1/images/wdbgp mounts=wdbgp-data envlist=wdbgp \
  start-on-boot=yes logging=yes
```

В RouterOS 7.22+ есть известная и пока не исправленная ошибка: рантайм
контейнеров не считывает `ENTRYPOINT`/`CMD` из манифеста некоторых образов
(включая этот, собранный `FROM scratch`), и контейнер не запускается с
ошибкой `start failed: no command specified, set cmd or entrypoint` (см.
[обсуждение на форуме MikroTik](https://forum.mikrotik.com/t/hap-ax3-after-update-ros-from-7-19-2-to-7-23-1-all-containers-fail-to-start/271024)).
Пока MikroTik не исправит это, обходите проблему явным указанием
`entrypoint` и `cmd` в последней строке `/container/add`:

```routeros
/container/add remote-image=wh1ted/wdbgp:latest interface=veth-wdbgp \
  root-dir=disk1/images/wdbgp mounts=wdbgp-data envlist=wdbgp \
  entrypoint=/usr/local/bin/wdbgp cmd=serve \
  start-on-boot=yes logging=yes
```

Разрешите в RouterOS firewall HTTP к порту 8080 из пользовательских сетей,
TCP/179 между контейнером и BGP peers, а также forwarding к полученным
destination-префиксам. Для IPv6 добавьте адрес контейнера и
`WDBGP_BGP_LOCAL_ADDRESS_V6`.

Для криптографической аутентификации динамических пиров на контейнерах
RouterOS 7.21+ (x86/ARM64) добавьте
`/container/envs/add list=wdbgp key=WDBGP_DYNAMIC_PEER_MD5_MATCH value="1"`
и установите `/container/set [find name=wdbgp] user=0:0` — контейнер сам
управляет своей настройкой NFQUEUE/nftables, но для этого ему нужно
работать от root. См.
[MD5-аутентификация динамических BGP-пиров](docs/dynamic-peer-md5.ru.md).

## Ограничения

- Изменение выбора маршрутов применяется без перезапуска; включение/выключение
  пира обновляет BGP-спикер динамически.
